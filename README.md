# Qubo for Home Assistant

Custom integration for Qubo video doorbells, cameras and smart door locks,
built on the [`qubopy`](https://github.com/selvakk2k/qubopy) client library.

Tested against a Qubo Video Doorbell Pro and an HLM04A Smart Door Lock on
Home Assistant 2026.10.

## Requirements

- Home Assistant 2024.12 or newer.
- A Qubo account that owns your hardware and can sign in with **email and
  password**. Accounts that sign in with a phone/SMS one-time code are not
  supported, because that login route returns a one-hour token with no refresh
  token, so the integration would have to re-authenticate constantly.

## Installation

This repository is private, so [HACS](https://hacs.xyz/) cannot install it —
HACS only serves public repositories. Install manually:

1. Copy the `custom_components/qubo` folder into your Home Assistant
   `config/custom_components` directory, so you end up with
   `config/custom_components/qubo/__init__.py`.
2. Restart Home Assistant.
3. Go to **Settings -> Devices & Services -> Add Integration** and search for
   **Qubo**.

Then open the entry's **Configure** button at any time to change the login name
described below.

## Setup

You need the email and password of the Qubo cloud account that owns the
hardware.

### Login name

`Name shown in the Qubo app` sets the label this integration signs in with. It
appears under *Account -> Logged In Devices* in the Qubo mobile app, where you
can also revoke the session. Changing it forces a fresh login under the new
name.

Two device ids are involved and they are deliberately kept apart:

- The **login device id** is generated by this integration and is the identity
  it signs in as.
- A **mobile device id** is only ever used as the `userAppID` the Qubo cloud
  requires when minting a stream URL. Logging in *as* the paired phone would
  share that app's session, so tapping "Logout" on your phone would break Home
  Assistant.

## Entities

| Entity | Type |
| --- | --- |
| `lock.smart_door_lock` | Lock |
| `sensor.smart_door_lock_battery` | Sensor |
| `camera.video_doorbell_pro` | Camera |
| `sensor.<doorbell>_last_doorbell_event` | Sensor |
| `switch.<doorbell>_do_not_disturb` | Switch |
| `switch.<doorbell>_chime_bell` | Switch |
| `switch.<doorbell>_privacy_mode` | Switch |
| `switch.<doorbell>_tamper_alerts` | Switch |
| `switch.<doorbell>_timelapse_generator` | Switch |
| `switch.<lock>_silent_mode` | Switch |
| `button.<doorbell>_restart` | Button |
| `sensor.<doorbell>_wi_fi_network` | Sensor (diagnostic) |
| `sensor.<doorbell>_reported_time_zone` | Sensor (diagnostic) |

Entity ids use your device names, so the exact ids will differ from the table
above if you named your devices differently.

- **Lock** — remote unlock only, relayed through the paired in-home gateway
  (the doorbell or camera in the same unit). The Qubo cloud cannot motorise the
  bolt back, so locking is deliberately refused with an explanatory error rather
  than silently doing nothing.
- **Battery** — lock battery percentage.
- **Camera** — live stream, plus wifi signal, wifi SSID, LAN IP, night mode,
  privacy mode and SD card status/free space as state attributes.
- **Last doorbell event** — when the doorbell last rang. Attributes carry the
  retained event count, last call status, and whether a recording and snapshot
  exist. The cloud keeps a rolling window (30 events observed).

### Switches and button

The doorbell switches mirror the settings the Qubo app shows on its device
screen — do not disturb, chime bell, privacy mode, tamper alerts and the
timelapse generator — plus the lock's silent mode.

Each is one writable shadow attribute. After you toggle a switch the
integration shows your choice immediately, then re-reads it on the next poll
and shows whatever the device actually reports. **A switch that flips back means
the device did not accept the change** — usually because it has not had recent
contact with the cloud.

The restart button sends the same `deviceReboot` command the app's *Restart
Your Device* row sends. The cloud only acknowledges the request; the doorbell
then drops off the network and returns on its own after a minute or two, so it
is unavailable for a while after pressing it.

The two diagnostic sensors report the SSID and time zone offset the doorbell
says it is using. They are read-only and exist to answer "is it configured the
way I think" without opening the app. Where they overlap the camera's state
attributes (`wifi_ssid`, `privacy_mode`), these are the authoritative ones —
they come from the v2 shadow with a device timestamp, while the camera
attributes come from the older v1 shadow that carries no timestamp.

## Known limitations

- **The cloud relays video.** Stream URLs are minted per viewer from the Qubo
  cloud and are single-consumer, so two viewers cannot watch at once and video
  leaves your LAN. For local video, see
  [docs/go2rtc.md](docs/go2rtc.md) — after a short handshake through the cloud,
  the doorbell streams straight to your machine and the media never leaves it.
- **No motion or person detection.** Qubo exposes no motion or person state for
  this hardware on any reachable interface, so no such entity is created rather
  than one that would read `unknown` forever. The device shadow, MQTT, the
  `ooi-events` endpoint, `facesDetected` and the ROI manager were all checked.
  Motion and person are still selectable as *recording triggers* in the Qubo
  app; they are simply not readable back as state.
- **No remote locking**, for the reason given above.
- **The lock does not report instantly.** It reports within tens of seconds
  when the in-home gateway has had recent contact with it. After an unlock the
  integration polls for up to three minutes waiting for the lock to actually
  report, rather than assuming the bolt moved.

## Implementation notes

The integration is pinned to `qubopy==0.2.0`, which handles authentication,
token refresh, device discovery, typed device objects and shadow parsing, and
covers the response shape of every request this integration sends.

Earlier versions had five defects that made them unusable here, all reported
upstream and fixed in 0.1.4:

- The cloud answers attribute writes and commands with HTTP 200 and the plain text
  `SUCCESS`. Older `qubopy` parsed every 2xx body as JSON, so a write that fully
  succeeded raised `Failed to parse server response as JSON`.
- `send_command()` and `update_shadow_attribute()` built the correct URLs but sent
  `POST`, where the cloud only accepts `PUT` (`405 Request method 'POST' not
  supported`).
- `get_all_shadows()` issued a `GET` the cloud rejects with 405.
- `get_device_events()` pointed at an endpoint that answers 405 or 404.
- The v1 shadow `qubopy` parses carries no timestamps, so a stale reading is
  indistinguishable from a fresh one. 0.1.4 adds `get_device_shadow_v2()`,
  which returns the value together with the moment the device last reported it.

`api.py` is the only module that still reaches past the library, and it now does
so for two narrow reasons:

- Reads go through `get_device_shadow_v2()` rather than the default v1 shadow,
  because a switch write cannot be confirmed without a device-side timestamp.
- Write paths are formatted in `api.py` rather than by the library's wrappers, so
  that a device missing its unit or entity binding fails loudly, naming the
  device, instead of addressing a guessed scope.

`Subscriber-Key` is the live access token, not the static 64-hex constant
embedded in the app binary; hardcoding the constant yields 401s.

Two `qubopy` behaviours are worth knowing about:

- **The refresh token is static, not rotating.** When a refresh response omits
  `refreshToken`, `qubopy` keeps the stored one — which is correct. The Qubo
  refresh token is a long-lived credential (JWT claim ~180 days), not a
  single-use one, and reusing it across hourly refreshes is what the vendor app
  does. A rejected refresh raises `QuboAuthError` and drops the token, so a
  genuinely expired one still surfaces as a re-login rather than a silent retry.
- **P2P signalling is all `qubopy` implements.** Since 0.2.0,
  `initiate_p2p_call()` accepts `mobile_uuid` and `src_device_id` overrides, so
  it can now address the doorbell the way a working session requires. It still
  stops at the `p2pCall` POST: the UDP handshake, AES-128-GCM decryption and
  FU-A reassembly are not in the library, and the media would have nowhere to go.
  Local P2P video therefore remains
  [docs/qubo_p2p_client.py](docs/qubo_p2p_client.py)'s job, which does the
  handshake and feeds ffmpeg.

### Upgrading

The requirement is pinned, so Home Assistant installs the right version on a fresh
setup. An **existing** install does not reinstall dependencies when files are
copied over `custom_components/` — install it manually before restarting Home
Assistant:

```
docker exec homeassistant pip install qubopy==0.2.0
```

## Tests

The tests stub `qubopy`, so they run without it installed and without network
access:

```
python -m pytest tests/
```

or individually:

```
python tests/test_shadow.py
python tests/test_writes.py
```

`test_shadow.py` pins the interpretation of the device's lock-state strings,
which is the one place a wrong answer means a door reads open when it is shut.
`test_writes.py` pins the exact request bodies sent to the cloud, since the
command body nests `instanceId` inside the command while the attribute-write
body has it at the top level — mixing them up earns a rejected write. It also
stubs `request()` the way 0.2.0 behaves, because the integration relies on the
library to accept the plain-text `SUCCESS` reply and to map 401/403 onto an auth
error.
